# Cagnard v0.12.0

Static login and OIDC SSO now share one identity, session, and authorization model. This release also updates the operator documentation with linked model references, migration guidance, and diagrams.

## Upgrade required: auth configuration v2

**Existing installations must migrate their configuration before upgrading.** Deploy the backend, frontend, and v2 configuration together. Legacy authentication fields and cookies are rejected, and users must sign in again.

Follow the [auth migration guide](https://github.com/k3rnL/cagnard/blob/v0.12.0/docs/guides/migrating-auth.md) and use the [complete static/OIDC configuration](https://github.com/k3rnL/cagnard/blob/v0.12.0/config/cagnard.oidc.example.conf).

- Declare application groups, roles with explicit actions, and bindings granting those roles on named roots. Access is denied without a matching binding.
- Preserve existing home paths with explicit storage keys. Matching usernames or emails across providers do not link identities or homes.
- Configure the exact public origin and a fresh session protection key. Browser mutations require the configured origin and application header.
- Back up the old configuration and retain matching old images for a coordinated rollback. Provider data is not rolled back with the application.

## Authentication and authorization

- Keep static accounts alongside OIDC, including an independently granted recovery account.
- OIDC uses backend authorization code exchange, PKCE S256, state, nonce, and ID-token verification. Group claims must be present in the ID token and explicitly mapped to declared application groups.
- Encrypted cookies carry bounded identity evidence. OIDC sessions expire at the earlier of ID-token expiry and the application TTL; there is no refresh-token flow.
- Storage APIs, previews, archives, Iceberg, transfers, and background work use centralized action checks. Account read-only restrictions still apply.
- Tasks belong to provider-qualified identities and run within authentication deadlines. Completed storage effects are retained after cancellation or expiry; eligible conflict continuation requires current authentication and permissions.
- A user with no grants stays signed in and sees a clear no-access state. A denied action does not log the user out.

Logout clears the local Cagnard session; it does not sign out of the IdP or revoke already accepted backend work. IdP membership changes take effect at the next sign-in, bounded by session expiry.

## Deployment and documentation

- Helm values and Compose defaults now consistently use v0.12.0 images. Start with the [Docker guide](https://github.com/k3rnL/cagnard/blob/v0.12.0/docs/getting-started/docker.md) or [Helm guide](https://github.com/k3rnL/cagnard/blob/v0.12.0/docs/getting-started/helm.md); the base Helm configuration requires operator-provided auth secrets.
- A [local Keycloak exercise](https://github.com/k3rnL/cagnard/blob/v0.12.0/examples/run/oidc-keycloak/README.md) provides static, SSO, and unassigned demo users.
- MinIO examples and S3 CI build their test service from pinned official source commits, replacing unavailable upstream images. The first run takes longer while those images build.
- The [documentation index](https://github.com/k3rnL/cagnard/blob/v0.12.0/docs/README.md) links diagrams for auth models, OIDC, access decisions, storage targeting, deployment, task lifecycle, moves, and analytical processing.

Validation includes the Go race suite, 133 frontend tests, frontend and container builds, WASM demo checks, live Keycloak login, MinIO streaming/download/Iceberg integration tests, Helm/Compose validation, and documentation checks.
